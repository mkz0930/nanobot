## 📖 核心概念详解

### 1. Agent（代理）

**定义**: Agent 是 nanobot 的大脑，负责理解用户意图、规划任务、调用工具并生成响应。

**核心文件**: `nanobot/agent/loop.py`

**Agent 的组成**:
```python
class AgentLoop:
    def __init__(self, bus, provider, workspace, ...):
        self.bus = bus                    # 消息总线
        self.provider = provider          # LLM 提供商
        self.workspace = workspace        # 工作区路径
        self.context = ContextBuilder()   # 上下文构建器
        self.tools = ToolRegistry()       # 工具注册表
        self.sessions = SessionManager()  # 会话管理器
        self.subagents = SubagentManager() # 子代理管理器
```

**Agent 的工作流程**:
```
1. 接收消息 (InboundMessage)
   ↓
2. 加载会话历史
   ↓
3. 构建上下文 (系统提示 + 历史 + 记忆 + 技能)
   ↓
4. 调用 LLM
   ↓
5. 解析响应
   ├─ 纯文本 → 直接返回
   └─ 工具调用 → 执行工具 → 继续循环
   ↓
6. 保存会话历史
   ↓
7. 发送响应 (OutboundMessage)
```

**实践: 阅读 Agent Loop 源码**

```bash
# 打开核心文件
cat nanobot/agent/loop.py | head -150
```

**关键方法**:
- `process_message()`: 处理单条消息
- `_run_agent_loop()`: Agent 主循环
- `_register_default_tools()`: 注册默认工具

### 2. Tools（工具）

**定义**: 工具是 Agent 与外部世界交互的能力，如读写文件、执行命令、搜索网页等。

**核心文件**: `nanobot/agent/tools/base.py`

**工具基类结构**:
```python
class Tool(ABC):
    @property
    def name(self) -> str:
        """工具名称，如 'read_file'"""

    @property
    def description(self) -> str:
        """工具描述，告诉 LLM 这个工具的作用"""

    @property
    def parameters(self) -> dict[str, Any]:
        """JSON Schema 格式的参数定义"""

    async def execute(self, **kwargs) -> str:
        """执行工具逻辑，返回字符串结果"""
```

**内置工具清单**:

| 工具 | 文件 | 功能 |
|------|------|------|
| `read_file` | `filesystem.py` | 读取文件内容 |
| `write_file` | `filesystem.py` | 写入文件 |
| `edit_file` | `filesystem.py` | 编辑文件（查找替换）|
| `list_dir` | `filesystem.py` | 列出目录内容 |
| `exec` | `shell.py` | 执行 Shell 命令 |
| `web_search` | `web.py` | 网页搜索（Brave API）|
| `web_fetch` | `web.py` | 抓取网页内容 |
| `send_message` | `message.py` | 发送消息到频道 |
| `spawn` | `spawn.py` | 创建子代理 |
| `cron` | `cron.py` | 管理定时任务 |

**工具注册机制**:
```python
# 在 AgentLoop 中注册工具
registry = ToolRegistry()
registry.register(ReadFileTool())
registry.register(ExecTool())

# LLM 调用工具时
tool = registry.get("read_file")
result = await tool.execute(path="/path/to/file")
```

### 3. Skills（技能）

**定义**: 技能是 Markdown 格式的知识文档，教会 Agent 如何使用特定工具或完成特定任务。

**核心文件**: `nanobot/agent/skills.py`

**技能的结构**:
```
skills/
└── github/
    └── SKILL.md
```

**SKILL.md 格式**:
```markdown
---
name: github
description: "使用 gh CLI 与 GitHub 交互"
metadata:
  nanobot:
    emoji: "🐙"
    requires:
      bins: ["gh"]  # 需要的二进制工具
    install:        # 安装指南
      - id: "brew"
        kind: "brew"
        formula: "gh"
---

# GitHub Skill

使用 `gh` CLI 与 GitHub 交互...

## 示例

\`\`\`bash
gh pr list --repo owner/repo
\`\`\`
```

**技能加载机制**:

```python
class SkillsLoader:
    def list_skills(self):
        """列出所有可用技能"""

    def load_skill(self, name: str):
        """加载指定技能的内容"""

    def get_always_skills(self):
        """获取始终加载的技能"""

    def build_skills_summary(self):
        """构建技能摘要（名称 + 描述）"""
```

**渐进式加载策略**:
1. **Always-loaded skills**: 完整内容加载到上下文
2. **Available skills**: 仅显示摘要，Agent 按需使用 `read_file` 加载

**为什么这样设计？**
- 节省 token（上下文长度有限）
- 提高响应速度
- 保持灵活性

```bash
# 查看天气技能

# 列出所有技能
```

### 4. Providers（提供商）

**定义**: Provider 是 LLM 服务提供商的抽象层，统一不同 API 的调用方式。

**核心文件**: `nanobot/providers/registry.py`

**Provider Registry 模式**:

所有 Provider 元数据集中在 `PROVIDERS` 元组中：

```python
@dataclass(frozen=True)
class ProviderSpec:
    name: str                    # 配置字段名
    keywords: tuple[str, ...]    # 模型名关键词
    env_key: str                 # 环境变量名
    display_name: str            # 显示名称
    litellm_prefix: str          # LiteLLM 前缀
    skip_prefixes: tuple         # 跳过前缀
    is_gateway: bool             # 是否为网关
    # ... 更多字段
```

**示例: OpenRouter Provider**:
```python
ProviderSpec(
    name="openrouter",
    keywords=("openrouter",),
    env_key="OPENROUTER_API_KEY",
    display_name="OpenRouter",
    litellm_prefix="openrouter",
    is_gateway=True,
    detect_by_key_prefix="sk-or-",
    default_api_base="https://openrouter.ai/api/v1",
)
```

**Provider 的作用**:
1. **统一接口**: 不同 Provider 使用相同的调用方式
2. **自动前缀**: 自动为模型名添加前缀（如 `claude-3` → `openrouter/claude-3`）
3. **环境变量**: 自动设置 LiteLLM 需要的环境变量
4. **网关检测**: 自动识别网关型 Provider（如 OpenRouter）

**实践: 查看 Provider 配置**

```bash
# 查看 Provider Registry
cat nanobot/providers/registry.py | head -200

# 查看配置 Schema
```

### 5. Channels（频道）

**定义**: Channel 是与聊天平台的集成，负责接收和发送消息。

**核心文件**: `nanobot/channels/base.py`

**Channel 基类**:
```python
class BaseChannel(ABC):
    async def start(self):
        """启动频道，开始监听消息"""

    async def stop(self):
        """停止频道"""

    async def send_message(self, chat_id: str, content: str):
        """发送消息到指定聊天"""
```

**支持的 Channel**:

| Channel | 文件 | 连接方式 |
|---------|------|----------|
| Telegram | `telegram.py` | Bot API |
| Discord | `discord.py` | WebSocket Gateway |
| WhatsApp | `whatsapp.py` | Bridge (Node.js) |
| Feishu | `feishu.py` | WebSocket 长连接 |
| DingTalk | `dingtalk.py` | Stream Mode |
| Slack | `slack.py` | Socket Mode |
| Mochat | `mochat.py` | Socket.IO |
| Email | `email.py` | IMAP/SMTP 轮询 |
| QQ | `qq.py` | botpy SDK |

**Channel 的工作流程**:
```
1. 启动 Channel
   ↓
2. 监听平台消息
   ↓
3. 转换为 InboundMessage
   ↓
4. 发布到消息总线
   ↓
5. 等待 OutboundMessage
   ↓
6. 转换为平台格式
   ↓
7. 发送到平台
```

### 6. Message Bus（消息总线）

**定义**: 消息总线是事件驱动架构的核心，负责消息的路由和分发。

**核心文件**: `nanobot/bus/events.py`, `nanobot/bus/queue.py`

**消息类型**:
```python
@dataclass
class InboundMessage:
    """接收的消息"""
    channel: str      # 来源频道 (telegram, discord, ...)
    sender_id: str    # 发送者 ID
    chat_id: str      # 会话 ID
    content: str      # 消息内容
    timestamp: datetime
    media: list[str]  # 媒体文件 URL
    metadata: dict    # 频道特定元数据

@dataclass
class OutboundMessage:
    """发送的消息"""
    channel: str
    chat_id: str
    content: str
    reply_to: str | None
    media: list[str]
    metadata: dict
```

**消息总线的作用**:
1. **解耦**: Channel 和 Agent 不直接通信
2. **异步**: 支持异步消息处理
3. **多对多**: 多个 Channel 可以连接到同一个 Agent

**消息流示意图**:
```
Telegram Channel ──┐
                   │
Discord Channel ───┼──→ Message Bus ──→ Agent Loop
                   │
Slack Channel ─────┘

Agent Loop ──→ Message Bus ──┬──→ Telegram Channel
                             │
                             ├──→ Discord Channel
                             │
                             └──→ Slack Channel
```

## 🔍 深入理解

### 设计模式分析

#### 1. 注册表模式 (Registry Pattern)

**应用**: `ToolRegistry`, `ProviderRegistry`

**优点**:
- 集中管理
- 易于扩展
- 避免硬编码

**示例**:
```python
# 注册
registry.register(MyTool())

# 查找
tool = registry.get("my_tool")

# 列出所有
tools = registry.list_all()
```

#### 2. 策略模式 (Strategy Pattern)

**应用**: `Provider` 系统

**优点**:
- 统一接口
- 可替换实现
- 易于测试

**示例**:
```python
# 不同 Provider，相同接口
response = await provider.complete(messages, model)
```

#### 3. 发布-订阅模式 (Pub-Sub Pattern)

**应用**: `MessageBus`

**优点**:
- 解耦组件
- 支持异步
- 易于扩展

**示例**:
```python
# 发布
await bus.publish_inbound(message)

# 订阅
async for msg in bus.subscribe_inbound():
    process(msg)
```

### 为什么这样设计？

**Q: 为什么工具返回字符串而不是结构化数据？**

A: 因为 LLM 更容易理解自然语言描述。字符串结果可以直接作为上下文继续对话。

**Q: 为什么使用 Provider Registry 而不是 if-elif？**

A: Registry 模式更易扩展。添加新 Provider 只需添加一个 ProviderSpec，不需要修改现有代码。

**Q: 为什么技能使用 Markdown 而不是 Python 代码？**

A: Markdown 更易读、易写、易维护。非技术人员也可以创建技能。

## 📚 阶段 1-2: 核心架构理解

### 1. 消息总线事件 (`01-events.py`)

**核心概念**：事件驱动架构的基础数据结构

```python
@dataclass
class InboundMessage:
    """接收的消息（从聊天平台到 Agent）"""
    channel: str      # 平台名称：telegram, discord, slack
    sender_id: str    # 发送者 ID
    chat_id: str      # 聊天 ID
    content: str      # 消息内容
    timestamp: datetime
    media: list[str]  # 媒体文件 URL
    metadata: dict    # 平台特定数据

    @property
    def session_key(self) -> str:
        """会话唯一标识：channel:chat_id"""
        return f"{self.channel}:{self.chat_id}"
```

**关键设计**：
- 使用 `@dataclass` 自动生成构造函数和方法
- `session_key` 用于区分不同对话会话
- `metadata` 存储平台特定信息（如消息 ID、回复信息）

**消息流程**：
```
Telegram Channel → InboundMessage → Message Bus → Agent Loop
Agent Loop → OutboundMessage → Message Bus → Telegram Channel
```

### 2. 上下文构建器 (`context.py`)

**核心概念**：组装 Agent 的完整上下文

```python
class ContextBuilder:
    """构建 Agent 的系统提示和消息列表"""

    def __init__(self, workspace: Path):
        self.workspace = workspace
        self.memory = MemoryStore(workspace)      # 记忆存储
        self.skills = SkillsLoader(workspace)     # 技能加载器

    def build_system_prompt(self) -> str:
        """构建系统提示"""
        parts = []
        parts.append(self._get_identity())        # 核心身份
        parts.append(self._load_bootstrap_files()) # 引导文件
        parts.append(self.memory.get_memory_context()) # 记忆
        parts.append(self.skills.build_skills_summary()) # 技能摘要
        return "\\n\\n---\\n\\n".join(parts)
```

**上下文组成**：
1. **核心身份** - Agent 的基本信息和能力
2. **引导文件** - AGENTS.md, SOUL.md, USER.md 等
3. **记忆上下文** - 从 memory/MEMORY.md 加载
4. **技能摘要** - 可用技能列表（渐进式加载）

**渐进式技能加载**：
- **Always-loaded skills**: 完整内容加载到上下文
- **Available skills**: 仅显示摘要，Agent 按需使用 `read_file` 加载

**为什么这样设计？**
- 节省 token（上下文长度有限）
- 提高响应速度
- 保持灵活性

### 3. Agent 主循环 (`loop.py`)

**核心概念**：Agent 的大脑，处理消息和工具调用

```python
class AgentLoop:
    """Agent 主循环 - 核心处理引擎"""

    def __init__(self, bus, provider, workspace, ...):
        self.bus = bus                    # 消息总线
        self.provider = provider          # LLM 提供商
        self.workspace = workspace        # 工作区路径
        self.context = ContextBuilder()   # 上下文构建器
        self.tools = ToolRegistry()       # 工具注册表
        self.sessions = SessionManager()  # 会话管理器
        self.subagents = SubagentManager() # 子代理管理器

    async def process_message(self, msg: InboundMessage):
        """处理单条消息"""
        # 1. 加载会话历史
        history = self.sessions.load(msg.session_key)

        # 2. 构建消息列表
        messages = self.context.build_messages(history, msg.content)

        # 3. 运行 Agent 循环
        response = await self._run_agent_loop(messages)

        # 4. 保存会话历史
        self.sessions.save(msg.session_key, messages)

        # 5. 发送响应
        await self.bus.publish_outbound(OutboundMessage(...))
```

**Agent Loop 流程**：
```
1. 接收消息 (InboundMessage)
   ↓
2. 加载会话历史
   ↓
3. 构建上下文 (系统提示 + 历史 + 记忆 + 技能)
   ↓
4. 调用 LLM
   ↓
5. 解析响应
   ├─ 纯文本 → 直接返回
   └─ 工具调用 → 执行工具 → 继续循环
   ↓
6. 保存会话历史
   ↓
7. 发送响应 (OutboundMessage)
```

**工具调用循环**：
```python
async def _run_agent_loop(self, messages):
    """Agent 主循环 - 支持多轮工具调用"""
    for iteration in range(self.max_iterations):
        # 调用 LLM
        response = await self.provider.complete(messages, tools)

        # 如果没有工具调用，返回文本响应
        if not response.tool_calls:
            return response.content

        # 执行所有工具调用
        for tool_call in response.tool_calls:
            tool = self.tools.get(tool_call.name)
            result = await tool.execute(**tool_call.arguments)
            messages.append({"role": "tool", "content": result})

        # 继续下一轮（LLM 会根据工具结果继续思考）
```

**关键设计**：
- **迭代限制** - `max_iterations` 防止无限循环
- **工具注册表** - 统一管理所有工具
- **会话管理** - 支持多用户并发对话
- **子代理** - 支持后台任务执行

## 🛠️ 阶段 3: 工具系统深入

### 4. 工具基类 (`04-tool-base.py`)

**核心概念**：所有工具的抽象基类

```python
class Tool(ABC):
    """工具抽象基类"""

    @property
    @abstractmethod
    def name(self) -> str:
        """工具名称（如 read_file）"""
        pass

    @property
    @abstractmethod
    def description(self) -> str:
        """工具描述（告诉 LLM 这个工具的作用）"""
        pass

    @property
    @abstractmethod
    def parameters(self) -> dict[str, Any]:
        """参数定义（JSON Schema 格式）"""
        pass

    @abstractmethod
    async def execute(self, **kwargs: Any) -> str:
        """执行工具逻辑，返回字符串结果"""
        pass
```

**为什么返回字符串？**
- LLM 更容易理解自然语言描述
- 字符串结果可以直接作为上下文继续对话
- 避免复杂的数据结构序列化问题

**JSON Schema 示例**：
```python
{
    "type": "object",
    "properties": {
        "path": {
            "type": "string",
            "description": "File path to read"
        },
        "encoding": {
            "type": "string",
            "enum": ["utf-8", "gbk"],
            "description": "File encoding"
        }
    },
    "required": ["path"]
}
```

**参数验证**：
```python
def validate_params(self, params: dict[str, Any]) -> list[str]:
    """验证参数是否符合 JSON Schema"""

    # 字符串长度检查（minLength, maxLength）
```

### 5. 文件操作工具 (`filesystem.py`)

**核心工具**：
- `ReadFileTool` - 读取文件内容
- `WriteFileTool` - 写入文件
- `EditFileTool` - 编辑文件（查找替换）
- `ListDirTool` - 列出目录内容

**ReadFileTool 示例**：
```python
class ReadFileTool(Tool):
    @property
    def name(self) -> str:
        return "read_file"

    @property
    def description(self) -> str:
        return "Read the contents of a file"

    @property
    def parameters(self) -> dict[str, Any]:
        return {
            "type": "object",
            "properties": {
                "path": {
                    "type": "string",
                    "description": "Path to the file"
                }
            },
            "required": ["path"]
        }

    async def execute(self, **kwargs: Any) -> str:
        path = Path(kwargs["path"])
        try:
            content = path.read_text(encoding="utf-8")
            return f"File: {path}\\n\\n{content}"
        except Exception as e:
            return f"Error reading file: {e}"
```

**沙箱模式**：
```python
if self.restrict_to_workspace:
    # 检查路径是否在工作区内
    if not path.resolve().is_relative_to(self.workspace):
        return "Error: Access denied (outside workspace)"
```

### 6. Shell 执行工具 (`shell.py`)

**核心概念**：执行 Shell 命令

```python
class ExecTool(Tool):
    @property
    def name(self) -> str:
        return "exec"

    async def execute(self, **kwargs: Any) -> str:
        command = kwargs["command"]

        # 沙箱模式检查
        if self.restrict_to_workspace:
            # 检查命令是否安全
            if self._is_dangerous_command(command):
                return "Error: Command not allowed in sandbox mode"

        # 执行命令
        process = await asyncio.create_subprocess_shell(
            command,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
            cwd=self.workspace
        )

        # 等待完成（带超时）
        stdout, stderr = await asyncio.wait_for(
            process.communicate(),
            timeout=self.timeout
        )

        return f"Exit code: {process.returncode}\\n{stdout.decode()}"
```

**安全考虑**：
- **超时限制** - 防止命令无限运行
- **沙箱模式** - 限制危险命令
- **工作目录** - 在工作区内执行

## 🤖 阶段 5: Provider 系统掌握

### 8. Provider 注册表 (`registry.py`)

**核心概念**：集中管理 LLM Provider 元数据

```python
@dataclass(frozen=True)
class ProviderSpec:
    """Provider 元数据"""
    name: str                    # 配置字段名
    keywords: tuple[str, ...]    # 模型名关键词
    env_key: str                 # 环境变量名
    display_name: str            # 显示名称
    litellm_prefix: str          # LiteLLM 前缀
    skip_prefixes: tuple         # 跳过前缀
    is_gateway: bool             # 是否为网关
    # ... 更多字段

# 所有 Provider 元数据集中在这里
PROVIDERS = (
    ProviderSpec(
        name="openrouter",
        keywords=("openrouter",),
        env_key="OPENROUTER_API_KEY",
        display_name="OpenRouter",
        litellm_prefix="openrouter",
        is_gateway=True,
        detect_by_key_prefix="sk-or-",
        default_api_base="https://openrouter.ai/api/v1",
    ),
    ProviderSpec(
        name="anthropic",
        keywords=("anthropic", "claude"),
        env_key="ANTHROPIC_API_KEY",
        display_name="Anthropic",
        litellm_prefix="anthropic",
        is_gateway=False,
    ),
    # ... 更多 Provider
)
```

**Provider Registry 模式的优势**：
1. **单一数据源** - 所有 Provider 信息集中管理
2. **易于扩展** - 添加新 Provider 只需添加一个 ProviderSpec
3. **自动处理** - 自动设置环境变量、模型前缀等
4. **避免 if-elif** - 不需要硬编码的条件判断

**添加新 Provider 的步骤**：
1. 在 `registry.py` 的 `PROVIDERS` 中添加 `ProviderSpec`
2. 在 `config/schema.py` 的 `ProvidersConfig` 中添加字段

**自动前缀处理**：
```python
# 用户配置: model = "claude-opus-4-5"
# Provider: litellm_prefix = "anthropic"
# 实际调用: "anthropic/claude-opus-4-5"

# 网关型 Provider (is_gateway=True)
# 用户配置: model = "anthropic/claude-opus-4-5"
# Provider: litellm_prefix = "openrouter"
# 实际调用: "openrouter/anthropic/claude-opus-4-5"
```

## 📊 核心设计模式总结

### 1. 注册表模式 (Registry Pattern)
**应用**: `ToolRegistry`, `ProviderRegistry`

**优点**:
- 集中管理
- 易于扩展
- 避免硬编码

**示例**:
```python
# 注册
registry.register(MyTool())

# 查找
tool = registry.get("my_tool")

# 列出所有
tools = registry.list_all()
```

### 2. 策略模式 (Strategy Pattern)
**应用**: `Provider` 系统

**优点**:
- 统一接口
- 可替换实现
- 易于测试

**示例**:
```python
# 不同 Provider，相同接口
response = await provider.complete(messages, model)
```

### 3. 发布-订阅模式 (Pub-Sub Pattern)
**应用**: `MessageBus`

**优点**:
- 解耦组件
- 支持异步
- 易于扩展

**示例**:
```python
# 发布
await bus.publish_inbound(message)

# 订阅
async for msg in bus.subscribe_inbound():
    process(msg)
```
